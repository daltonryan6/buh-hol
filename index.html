Welcome & Setup

0:00 – 0:10 00_setup.sql

Scenario

You work with Epic Clarity data. Today, Snowlift/Snowloader stages Clarity extracts into Snowflake, and Snowforge orchestrates SQL transformations. In this lab, you will replace that manual pipeline with dynamic tables, connect version-controlled SQL via Git workspaces, and protect sensitive patient data with tags and masking.

What we will build

  1. Git Workspaces – Connect a GitHub repo and run SQL directly from it
  2. Dynamic Tables – Declarative pipelines: INBOUND → CURATED → GOLD
  3. Power BI & Iceberg – Connection options, open-format gold layer, Fabric cost
  4. Tags & Governance – PII tagging, tag-based masking, role-based access

Prerequisites

  1. Snowflake trial – signup.snowflake.com (Enterprise, any cloud/region)
  2. Log in with ACCOUNTADMIN
  3. Clone the lab repo or download the scripts/ folder

Run the setup script

Open scripts/00_setup.sql and run it end-to-end. It creates the BUH_HOL database with INBOUND, CURATED, GOLD, and GOVERNANCE schemas, plus five Epic Clarity source tables with synthetic clinical data.

Expected output (checkpoint query)

CLARITY_SER8
HSP_ACCT_DX_LIST30
ORDER_PROC28

Clarity naming conventions: The INBOUND tables use Epic's actual column names – PAT_ENC_CSN_ID (encounter key), ENC_TYPE_C (numeric type codes like 1=Inpatient, 3=Emergency), RESULT_FLAG_C (0=Normal, 1=High, 2=Low). Dynamic tables will decode these into readable values.

Dynamic Tables (Hands-On)

0:25 – 1:05 02_dynamic_tables.sql

Dynamic tables flip ETL: you declare what the result should look like, and Snowflake handles when to refresh. No cron jobs, no orchestration, no manual MERGE scripts. This replaces what Snowforge does today.

2.1 Build the CURATED layer

Run Part B in the script. Five dynamic tables transform messy Clarity sources into a clean dimensional model:

SQL – FACT_ENCOUNTER (decodes Clarity type codes)
CREATE OR REPLACE DYNAMIC TABLE BUH_HOL.CURATED.FACT_ENCOUNTER
  TARGET_LAG = '1 minute'
  WAREHOUSE = COMPUTE_WH
AS
SELECT
    e.PAT_ENC_CSN_ID AS ENCOUNTER_ID,
    e.PAT_ID,
    CASE e.ENC_TYPE_C
        WHEN 1 THEN 'Inpatient'
        WHEN 2 THEN 'Outpatient'
        WHEN 3 THEN 'Emergency'
        WHEN 4 THEN 'Observation'
    END AS ENCOUNTER_TYPE,
    ...
FROM BUH_HOL.INBOUND.PAT_ENC e
LEFT JOIN BUH_HOL.INBOUND.CLARITY_SER s
  ON e.VISIT_PROV_ID = s.PROV_ID;
Dynamic TableSourceKey transformation
DIM_PATIENTPATIENTINITCAP names, format phones, compute age
DIM_PROVIDERCLARITY_SERFilter active, decode Y/N to boolean
FACT_ENCOUNTERPAT_ENC + CLARITY_SERDecode ENC_TYPE_C, compute LOS
FACT_DIAGNOSISHSP_ACCT_DX_LIST + PAT_ENCAdd IS_PRIMARY flag, join department
FACT_ORDERORDER_PROC + PAT_ENCDecode RESULT_FLAG_C (Normal/High/Low)

2.2 Build the GOLD layer

GOLD reads from CURATED (which reads INBOUND). The whole graph refreshes automatically:

Gold TablePurpose
DEPARTMENT_DASHBOARDEncounter counts, avg LOS, charges by department
ED_THROUGHPUTED arrival-to-discharge hours, primary diagnosis
READMISSION_RISKPatients with 2+ encounters within 30 days

SELECT * FROM BUH_HOL.GOLD.DEPARTMENT_DASHBOARD ORDER BY TOTAL_CHARGES DESC;
SELECT * FROM BUH_HOL.GOLD.ED_THROUGHPUT ORDER BY CONTACT_DATE;
SELECT * FROM BUH_HOL.GOLD.READMISSION_RISK ORDER BY DAYS_BETWEEN;

2.4 Monitor pipeline health

SQL – Refresh history
SELECT NAME, STATE, REFRESH_START_TIME,
       DATEDIFF('second', REFRESH_START_TIME, REFRESH_END_TIME) AS SECONDS
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY())
ORDER BY REFRESH_START_TIME DESC LIMIT 15;
TARGET_LAG guidance: 1 minute = ED throughput / real-time clinical. 15 minutes = operational reporting. 1 hour = standard analytics. DOWNSTREAM = refresh only when needed. Louis reported: DTs used similar credits to the existing ETL but saved significant engineering time – the value is in the orchestration code you no longer maintain.

Power BI, Iceberg & Fabric

1:05 – 1:20 03_powerbi_iceberg_fabric.sql

3.1 Three Power BI connection options

OptionHow it worksSF compute costBest for
DirectQueryPBI sends SQL at query timeWarehouse runs during dashboard useOperational dashboards
ImportPBI extracts data on a scheduleWarehouse runs only during refreshExecutive dashboards
Direct Lake (Fabric)SF writes Iceberg to OneLake; PBI reads ParquetWarehouse only writes IcebergMinimizing SF compute for BI

3.2 Fabric CU overconsumption

Watch for this: All Fabric workloads share one Capacity Unit (CU) pool. Direct Lake reads, Dataflows, Spark, SQL endpoints – all pull from the same pool. The cheapest path: keep your pipeline in Snowflake, write only GOLD as Iceberg to OneLake, size Fabric capacity for BI read load only.

3.3 Iceberg table (hands-on)

Iceberg tables use the same SQL but store data in open Parquet format. Any Iceberg-compatible engine (Fabric, Spark, Trino) can read it.

SQL – Query Iceberg table
SELECT * FROM BUH_HOL.GOLD.DEPT_DASHBOARD_ICEBERG
ORDER BY TOTAL_CHARGES DESC;

3.4 When to use which table type

LayerRecommendedWhy
INBOUNDSnowflake defaultFast ingest, time travel, streams
CURATEDSnowflake default (DT)Joins, transforms, incremental refresh
GOLD / DatamartIceberg (OneLake)Open format, Direct Lake, no SF compute for BI

3.5 Purview quick reference

You understand the three PBI options, why Fabric CUs matter, how Iceberg works, and the recommended hybrid pattern.

Tags, Sensitivity & Governance

1:20 – 1:40 04_tags_and_governance.sql

4.1 Where can tags be applied?

ObjectExample tag
Warehousecost_center = 'Analytics'
Databasesensitivity = 'CONFIDENTIAL'
Table / Viewcontains_phi = 'Yes'
Columnpii_type = 'SSN'

Tags cannot be applied to rows, stages, users, or roles.

4.2 Tag Clarity source columns

Run Parts B and C. The script tags sensitive columns on INBOUND.PATIENT using Clarity column names:

SQL – Apply PII tags
ALTER TABLE BUH_HOL.INBOUND.PATIENT MODIFY COLUMN SSN
  SET TAG BUH_HOL.GOVERNANCE.PII_TYPE = 'SSN';
ALTER TABLE BUH_HOL.INBOUND.PATIENT MODIFY COLUMN PAT_MRN_ID
  SET TAG BUH_HOL.GOVERNANCE.PII_TYPE = 'MRN';
ALTER TABLE BUH_HOL.INBOUND.PATIENT MODIFY COLUMN EMAIL_ADDRESS
  SET TAG BUH_HOL.GOVERNANCE.PII_TYPE = 'EMAIL';
-- ... and PAT_FIRST_NAME, PAT_LAST_NAME, HOME_PHONE, ADD_LINE_1, BIRTH_DATE

4.3 Tag-based masking

The key pattern: attach a masking policy to a tag, not individual columns. Every column with that tag is automatically protected.

SQL – One policy protects all PII
ALTER TAG BUH_HOL.GOVERNANCE.PII_TYPE SET
  MASKING POLICY BUH_HOL.GOVERNANCE.MASK_PII_STRING;

4.4 Test masking across roles

SQL – POLICY_CONTEXT testing
-- ADMIN sees everything
EXECUTE USING POLICY_CONTEXT(CURRENT_ROLE => 'BUH_LAB_ADMIN')
SELECT PAT_FIRST_NAME, PAT_LAST_NAME, SSN, EMAIL_ADDRESS, BIRTH_DATE
FROM BUH_HOL.INBOUND.PATIENT LIMIT 3;

-- CLINICIAN sees names/email, SSN last-4, DOB visible
EXECUTE USING POLICY_CONTEXT(CURRENT_ROLE => 'BUH_LAB_CLINICIAN')
SELECT PAT_FIRST_NAME, PAT_LAST_NAME, SSN, EMAIL_ADDRESS, BIRTH_DATE
FROM BUH_HOL.INBOUND.PATIENT LIMIT 3;

-- ANALYST sees ***MASKED*** for all PII
EXECUTE USING POLICY_CONTEXT(CURRENT_ROLE => 'BUH_LAB_ANALYST')
SELECT PAT_FIRST_NAME, PAT_LAST_NAME, SSN, EMAIL_ADDRESS, BIRTH_DATE
FROM BUH_HOL.INBOUND.PATIENT LIMIT 3;
