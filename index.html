2.3 Feature summary — all 8 dynamic tables

Here's the full picture of design choices across the pipeline:

LayerDynamic TableTARGET_LAGREFRESH_MODE
CORE_DATADIM_PATIENT1 minuteINCREMENTAL
CORE_DATADIM_PROVIDER1 minuteINCREMENTAL
CORE_DATAFACT_ENCOUNTER1 minuteADAPTIVE
CORE_DATAFACT_DIAGNOSIS1 minuteINCREMENTAL
CORE_DATAFACT_ORDER1 minuteINCREMENTAL
DATAMARTSDEPARTMENT_DASHBOARD15 minutesFULL
DATAMARTSED_THROUGHPUT1 minuteADAPTIVE
DATAMARTSREADMISSION_RISK15 minutesINCREMENTAL
Key design decision: TARGET_LAG controls freshness (how stale can it be?). REFRESH_MODE controls how the data is refreshed (incremental change processing, full rebuild, or adaptive). In production, set both explicitly — don't rely on defaults.
REFRESH_MODE best practices: ADAPTIVE is generally recommended for most workloads — it defaults to incremental refresh but auto-reinitializes when needed (e.g., bulk reloads). Use INCREMENTAL when you want to guarantee no reinitialization and you control upstream load patterns. Use FULL for heavy aggregations where a predictable full rebuild is simpler than tracking changes. Avoid non-deterministic functions like CURRENT_DATE() in dynamic table definitions — they prevent incremental refresh. Always set REFRESH_MODE explicitly; don't rely on AUTO in production.

2.4 Streams + Tasks — event-driven complement

Dynamic tables are declarative — you define the result, Snowflake handles refresh. But some workflows need imperative event-driven logic: audit logging, notifications, triggering external systems. That’s where Streams + Tasks come in.

A Stream captures row-level changes (inserts, updates, deletes) on a table. A Task runs SQL on a schedule — or only when a stream has data. Together they give you CDC-triggered side effects.

CoCo Prompt – Streams + Tasks audit log
Run Part E of scripts/02_dynamic_tables.sql — the Streams + Tasks section.

It creates a STREAM on INBOUND.PATIENT that captures changes, an audit log
table in the GOVERNANCE schema, and a TASK that runs every minute to log
new patient arrivals.

After everything is created, show me the stream and task status.
What’s happening: The stream is now watching INBOUND.PATIENT for any inserts, updates, or deletes. The task checks every minute — when the stream has data, it automatically logs the change to the audit table. No scheduling code needed. In the next step, we'll insert a new patient and see both the dynamic tables AND the audit log react.
PatternHow it worksBest for
Dynamic TablesDeclare the result — Snowflake figures out when and how to refreshTransformations, dimensional models, aggregations

2.6 Monitor pipeline health

SQL – Refresh history
SELECT NAME, STATE, REFRESH_START_TIME,
       DATEDIFF('second', REFRESH_START_TIME, REFRESH_END_TIME) AS SECONDS
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY())
ORDER BY REFRESH_START_TIME DESC LIMIT 15;

Platform Features

0:50 – 1:15 03_platform_features.sql

Your pipeline is running. Now let's explore platform features that complement it: instant environment cloning, cost controls, query caching, custom functions, and AI/ML.

3.1 Zero-Copy Cloning + Time Travel Recovery

Snowflake stores data as immutable micro-partitions (columnar, compressed). A clone creates a metadata-only copy that shares physical storage — it's instant and free until you write to the clone. Combined with time travel, this means even catastrophic mistakes are recoverable.

Worksheet walkthrough: Open scripts/03_platform_features.sql in your worksheet and follow along as we run Part A block by block. We'll clone the PATIENT table, accidentally delete all patients, use time travel to see the data before the mistake, and recover it — all live.
What just happened: The table clone was instant (metadata-only, zero storage cost). The accidental DELETE wiped all patients from the DEV copy — but the production table was completely untouched (clone isolation). Time travel let us query the table as it existed before the mistake, and a single INSERT...SELECT recovered every row. In production, Snowflake retains time travel history for 1–90 days depending on your edition.

3.2 Resource Monitors & Warehouse Isolation

Resource monitors track credit consumption and can notify or suspend a warehouse at configurable thresholds. Unlike Power BI’s shared capacity pool, each Snowflake warehouse is independent compute — one heavy ETL job can’t starve your BI queries.

CoCo Prompt – Resource monitor
Run Part B of scripts/03_platform_features.sql. It creates a resource
monitor with credit quota and notification triggers, attaches it to
our warehouse, and shows the monitor status.

Show me the SHOW RESOURCE MONITORS output.
No noisy neighbors: In production you'd run separate warehouses for ETL, analytics, and dev. Each has its own compute and can't starve the others — solving the "one big query kills everyone's dashboards" problem that shared capacity pools create.

3.3 Query Caching

Snowflake has two main cache layers: Result cache (24h, free, no warehouse needed) and warehouse local disk cache (SSD). A third remote storage layer operates transparently. This is especially important for Power BI — when 50 users open the same dashboard, only the first query runs.

Show me the query history comparison.

5.2 Fabric CU overconsumption

Watch for this: All Fabric workloads share one Capacity Unit (CU) pool. Direct Lake reads, Dataflows, Spark, SQL endpoints – all pull from the same pool. The cheapest path: keep your pipeline in Snowflake, write only DATAMARTS as Iceberg to OneLake, size Fabric capacity for BI read load only.

In production: You'd create an EXTERNAL VOLUME pointing to Microsoft OneLake, then write the Iceberg table there. Power BI reads via Direct Lake with zero Snowflake compute. The SQL is identical — you just add the EXTERNAL_VOLUME parameter. See Part D in the script for the full OneLake pattern.
LayerRecommendedWhy
INBOUNDSnowflake defaultFast ingest, time travel, streams
CORE_DATASnowflake default (DT)Joins, transforms, incremental refresh
