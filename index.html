Shared Workspaces & Git Integration

0:10 – 0:25 01_workspaces_and_git.sql

Workspaces connect a Git repo (GitHub, GitLab, Azure DevOps) to your Snowflake account. This lab itself was delivered via a Git workspace.

What you can do

  • Browse – Navigate repo files in Snowsight
  • Run – Execute .sql files without downloading
  • Version – Every change goes through Git
  • Collaborate – Team sees the same versioned code

How it works

SQL – Git integration setup
-- Step 1: API integration
CREATE OR REPLACE API INTEGRATION github_integration
  API_PROVIDER = GIT_HTTPS_API
  API_ALLOWED_PREFIXES = ('https://github.com/your-org/')
  ENABLED = TRUE;

-- Step 2: Git repository object
CREATE OR REPLACE GIT REPOSITORY BUH_HOL.RAW.LAB_REPO
  API_INTEGRATION = github_integration
  ORIGIN = 'https://github.com/daltonryan6/buh-hol.git';

-- Step 3: Fetch and browse
ALTER GIT REPOSITORY BUH_HOL.RAW.LAB_REPO FETCH;
LS @BUH_HOL.RAW.LAB_REPO/branches/main/scripts/;

Before vs After

Without Git workspacesWith Git workspaces
SQL in local files, Slack, shared drivesSQL versioned in Git with full history
No code review, no rollbackPull requests and peer review
"Which version is in prod?" – unknownTraceable: commit abc123 is in prod
Onboarding = copying files aroundClone and run
Why this matters: Your Snowflake account has a live, bidirectional connection to GitHub. You can pull latest changes, create branches, commit edits, push updates, and resolve merge conflicts – all from Snowsight.

Checkpoint

You understand Git integrations, repository objects, and how versioned SQL replaces file-share chaos.

Dynamic Tables

0:25 – 0:55 02_dynamic_tables.sql

Dynamic tables flip ETL: you declare what the result should look like, and Snowflake handles when to refresh. No scheduling, no orchestration, no manual MERGE scripts.

2.1 Build the CURATED layer

Run Part B in the script. Each dynamic table declares a transformation and a TARGET_LAG:

SQL – DIM_PATIENT example
CREATE OR REPLACE DYNAMIC TABLE BUH_HOL.CURATED.DIM_PATIENT
  TARGET_LAG = '1 minute'
  WAREHOUSE = COMPUTE_WH
AS
SELECT
    PAT_ID, PAT_MRN,
    INITCAP(PAT_FIRST_NAME) AS FIRST_NAME,
    INITCAP(PAT_LAST_NAME)  AS LAST_NAME,
    BIRTH_DATE,
    DATEDIFF('year', BIRTH_DATE, CURRENT_DATE()) AS AGE,
    SSN, PHONE, EMAIL, GENDER,
    LOAD_TS AS SOURCE_LOADED_AT
FROM BUH_HOL.RAW.PATIENT_DIM;

2.2 Build the GOLD layer

GOLD dynamic tables read from CURATED (which reads RAW). The whole graph refreshes automatically.

SQL – Query gold tables
SELECT * FROM BUH_HOL.GOLD.PATIENT_ENCOUNTER_SUMMARY ORDER BY TOTAL_CHARGES DESC;
SELECT * FROM BUH_HOL.GOLD.DEPARTMENT_DASHBOARD ORDER BY TOTAL_CHARGES DESC;
SELECT * FROM BUH_HOL.GOLD.ABNORMAL_RESULTS_SUMMARY;

2.3 Watch it refresh

Insert a new patient and see it propagate through all layers automatically:

SQL – Insert + verify
INSERT INTO BUH_HOL.RAW.PATIENT_DIM
  (PAT_ID,PAT_MRN,PAT_FIRST_NAME,PAT_LAST_NAME,BIRTH_DATE,SSN,
   ADDRESS_LINE_1,CITY,STATE,ZIP_CODE,PHONE,EMAIL,PRIM_LANGUAGE,GENDER)
VALUES ('P100009','MRN-900009','Elena','Vasquez','2001-02-14',
  '999-00-1111','500 Atwells Ave','Providence','RI','02909',
  '401-555-0109','evasquez@example.com','Spanish','Female');

-- Wait ~1 minute, then verify
SELECT * FROM BUH_HOL.CURATED.DIM_PATIENT WHERE PAT_ID = 'P100009';
SELECT * FROM BUH_HOL.GOLD.PATIENT_ENCOUNTER_SUMMARY WHERE PAT_ID = 'P100009';

2.4 Monitor pipeline health

SQL – Refresh history
SELECT NAME, STATE, REFRESH_START_TIME,
       DATEDIFF('second', REFRESH_START_TIME, REFRESH_END_TIME) AS SECONDS
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY())
ORDER BY REFRESH_START_TIME DESC LIMIT 15;
TARGET_LAG guidance: 1 minute = near real-time dashboards. 15 minutes = operational reporting. 1 hour = standard analytics. DOWNSTREAM = refresh only when a consumer needs it.

Checkpoint

7 dynamic tables (4 CURATED + 3 GOLD). New patient P100009 appears in all layers after refresh. Refresh history shows successful runs.

Power BI, Iceberg & Fabric

0:55 – 1:20 03_powerbi_iceberg_fabric.sql

3.1 Power BI connection options

OptionHow it worksSF compute costBest for
DirectQueryPBI sends SQL at query timeWarehouse runs during dashboard useOperational dashboards
ImportPBI extracts data on a scheduleWarehouse runs only during refreshExecutive dashboards
Direct Lake (Fabric)SF writes Iceberg to OneLake; PBI reads ParquetWarehouse only writes IcebergMinimizing SF compute for BI

3.2 Fabric consumption

Watch for Fabric CU overconsumption All Fabric workloads share one Capacity Unit pool. Direct Lake reads consume CUs from that same pool. The cheapest path: keep your pipeline in Snowflake, write only GOLD as Iceberg to OneLake, size Fabric capacity for BI read load only.

3.3 Iceberg tables (hands-on)

Iceberg tables use the same SQL as regular tables, but data is stored in open Parquet format. Any Iceberg-compatible engine can read it.

SQL – Query the Iceberg table
SELECT * FROM BUH_HOL.GOLD.DEPT_DASHBOARD_ICEBERG
ORDER BY TOTAL_CHARGES DESC;

3.4 Iceberg for OneLake

The Microsoft-recommended pattern: create an external volume pointing to OneLake, write Iceberg tables there, and Power BI reads via Direct Lake with no Snowflake warehouse cost.

3.5 Purview integration

Purview can scan Snowflake (tables, views, procedures, lineage). For Iceberg in OneLake, Purview sees both sides. However, Snowflake tags and Purview sensitivity labels are separate systems – they do not auto-sync.

3.6 When to use which table type

LayerRecommendedWhy
RAWSnowflake defaultFast ingest, time travel, streams
CURATEDSnowflake default (DT)Joins, transforms, incremental
GOLD / DatamartIceberg (OneLake)Open format, Direct Lake, no SF compute for BI

Checkpoint

You understand the three PBI options, why Fabric CUs matter, how Iceberg works, and that Purview/Snowflake tags are separate systems.

Tags, Sensitivity Labels & Governance

1:20 – 1:45 04_tags_and_governance.sql

4.1 Where do tags apply?

ObjectExample tag
Warehousecost_center = 'Research'
Databasedata_domain = 'Clinical'
Schemadata_layer = 'RAW'
Table / Viewcontains_phi = 'Yes'
Columnpii_type = 'SSN'

Tags cannot be applied to individual rows, stages, file formats, users, or roles.

4.2 Create and apply tags

Run Parts B and C in the script to create PII_TYPE, SENSITIVITY, DATA_DOMAIN, and COST_CENTER tags, then apply them.

4.3 Find all PII columns

SQL – Query TAG_REFERENCES
SELECT OBJECT_NAME AS TABLE_NAME, COLUMN_NAME, TAG_VALUE AS PII_TYPE
FROM SNOWFLAKE.ACCOUNT_USAGE.TAG_REFERENCES
WHERE TAG_NAME = 'PII_TYPE' AND DOMAIN = 'COLUMN'
  AND OBJECT_DATABASE = 'BUH_HOL'
ORDER BY TABLE_NAME, COLUMN_NAME;

4.4 Tag-based masking

Attach a masking policy to a tag, not individual columns. Every column with that tag is automatically protected.

SQL – Tag-based masking
ALTER TAG BUH_HOL.GOVERNANCE.PII_TYPE SET
  MASKING POLICY BUH_HOL.GOVERNANCE.MASK_PII_STRING;

4.5 Test masking across roles

SQL – POLICY_CONTEXT testing
-- ADMIN sees everything
EXECUTE USING POLICY_CONTEXT(CURRENT_ROLE => 'BUH_LAB_ADMIN')
SELECT PAT_FIRST_NAME, PAT_LAST_NAME, SSN, EMAIL, BIRTH_DATE
FROM BUH_HOL.RAW.PATIENT_DIM LIMIT 3;

-- CLINICIAN sees names, SSN last-4, DOB
EXECUTE USING POLICY_CONTEXT(CURRENT_ROLE => 'BUH_LAB_CLINICIAN')
SELECT PAT_FIRST_NAME, PAT_LAST_NAME, SSN, EMAIL, BIRTH_DATE
FROM BUH_HOL.RAW.PATIENT_DIM LIMIT 3;

-- ANALYST sees masked PII
EXECUTE USING POLICY_CONTEXT(CURRENT_ROLE => 'BUH_LAB_ANALYST')
SELECT PAT_FIRST_NAME, PAT_LAST_NAME, SSN, EMAIL, BIRTH_DATE
FROM BUH_HOL.RAW.PATIENT_DIM LIMIT 3;

4.6 Automatic classification

Snowflake auto-detects PII using SYSTEM$CLASSIFY. It scans column names and data patterns to recommend tags. In production, a classification profile does this on a schedule.

Putting It Together

1:45 – 1:55 05_putting_it_together.sql

Architecture

Architecture diagram
[Git Repo] --> [Snowflake Workspace]
     |
     v
RAW (default tables - Clarity extracts)
     |  dynamic tables auto-refresh
     v
CURATED (DIM_PATIENT, FACT_ENCOUNTER, FACT_LAB_RESULTS)
     |  dynamic tables auto-refresh
     v
GOLD (PATIENT_ENCOUNTER_SUMMARY, DEPT_DASHBOARD, ABNORMAL_RESULTS)
     |
     +--> Snowflake default tables (analytics, AI, sharing)
     |
     +--> Iceberg tables in OneLake (Power BI Direct Lake)

GOVERNANCE layer (tags + masking policies) applies across ALL layers

Verify end-to-end

SQL – Row counts
SELECT 'RAW.PATIENT_DIM' AS LAYER, COUNT(*) AS ROWS FROM BUH_HOL.RAW.PATIENT_DIM
UNION ALL SELECT 'CURATED.DIM_PATIENT', COUNT(*) FROM BUH_HOL.CURATED.DIM_PATIENT
UNION ALL SELECT 'CURATED.FACT_ENCOUNTER', COUNT(*) FROM BUH_HOL.CURATED.FACT_ENCOUNTER
UNION ALL SELECT 'GOLD.PATIENT_ENCOUNTER_SUMMARY', COUNT(*) FROM BUH_HOL.GOLD.PATIENT_ENCOUNTER_SUMMARY
UNION ALL SELECT 'GOLD.DEPARTMENT_DASHBOARD', COUNT(*) FROM BUH_HOL.GOLD.DEPARTMENT_DASHBOARD
ORDER BY LAYER;
